# RCA — BankEzee Connect CRM: "Copy Chatbot Link" fails in production

**Deployment:** responsive-crm-app-1 (connect.bankezee.com)
**Live run:** `7578da69-f83d-4558-8736-8c955c2a8f61` (redeploy, success, completed 2026-10-22T13:49:30Z)
**Live image:** `customers-app@sha256:a4f09839686b9ab8e75d3dde327b62fdcdad0c460145ef23b620bc0266503c22`
**Mode:** Diagnosis only — no code change, no redeploy performed.

## Symptom
On a Meta lead detail page, `POST /api/meta/leads/{lead_id}/chatbot/link` returns a Cloudflare "origin returned an invalid or incomplete response" gateway error (and, in captured instances, a 404).

## ROOT CAUSE — misconfigured prod secret causes a self-loop
The production (live-slot) value of **`BANKEZEE_CHATBOT_BASE_URL` is set to `https://connect.bankezee.com`** — the CRM app's OWN custom domain — instead of the chatbot server `https://bankezee.com`.

Confirmed via `list_secrets` metadata comparison (value itself never revealed):
- `== https://bankezee.com` → **matches_expected: false**
- `== https://www.bankezee.com` → **matches_expected: false**
- `== https://bankezee-seo-upgrade.preview.emergentagent.com` (the preview .env value) → **matches_expected: false**
- `== https://connect.bankezee.com` → **matches_expected: TRUE** ✅

Code path (from pulled source of the live run, `backend/routes/chatbot_integration.py`):
- line 43: `BASE_URL = (os.environ.get("BANKEZEE_CHATBOT_BASE_URL") or "").rstrip("/")`
- handler `create_or_renew_link` (line 337) → `_chatbot_request("POST", "/api/crm/chatbot/links")` (line 356)

So the handler makes a server-side outbound call to `POST {BASE_URL}/api/crm/chatbot/links` = `POST https://connect.bankezee.com/api/crm/chatbot/links`. Because `connect.bankezee.com` IS this same CRM app (routed via Cloudflare back to this backend), the request loops back onto itself. This CRM has no `/api/crm/chatbot/links` route → 404.

### Evidence of the self-loop (live-run backend logs)
Same pod's access log shows BOTH the inbound frontend request and the looped-back outbound target, the latter arriving from Cloudflare edge IPs (172.68.x / 104.23.x):
```
POST /api/meta/leads/lead_eba7b5e531b6/chatbot/link  404 Not Found   (from 172.68.166.170)
POST /api/crm/chatbot/links                          404 Not Found   (from 172.68.174.164, 104.23.160.91)
GET  /api/meta/leads/lead_eba7b5e531b6/chatbot        200 OK
```
Status histogram for the window: 200×2, 404×12. No 5xx, no worker timeout in logs.

The intermittent Cloudflare "invalid/incomplete response" is a product of the CRM calling its own origin back through the Cloudflare edge (a request-within-request loop on the same hostname); in the logged cases it surfaced cleanly as 404.

## Answers to the specific questions
1. **Which build is live / did the new deploy complete?** Yes. Run `7578da69` (the just-initiated redeploy) completed successfully at 13:49:30Z and is live. Deployed source for this run **includes** `backend/routes/chatbot_integration.py` and `backend/routes/whatsapp.py`, and the frontend **includes** `frontend/src/pages/meta/ChatbotQualificationCard.js` (referenced from `LeadDetail.js`). The feature code shipped correctly.
2. **Prod env vars set & non-empty?**
   - `BANKEZEE_CHATBOT_BASE_URL` — SET, non-empty, **but WRONG value** (`https://connect.bankezee.com`; should be `https://bankezee.com`). This is the root cause.
   - `BANKEZEE_CHATBOT_CRM_KEY` — SET, non-empty. ✅ (Not rejected by upstream — the request never reaches the real chatbot, so the key correctness can't be positively validated yet, but it is present.)
   - `META_WHATSAPP_ACCESS_TOKEN`, `META_WHATSAPP_APP_SECRET`, `META_WHATSAPP_VERIFY_TOKEN` — all SET, non-empty. ✅
3. **Can prod reach https://bankezee.com (egress/TLS)?** This is NOT the cause and was not exercised: the backend never calls the real `bankezee.com` — it calls `connect.bankezee.com` (itself). The 404s prove the outbound request completed (reached this app), so there is no egress hang/DNS/TLS failure involved. Egress to the real host is moot until the BASE_URL is corrected.
4. **Backend logs / pod health for that request:** HTTP 404 on both the inbound and the looped outbound request. No worker timeout, no 5xx. Pod events for the live run show both replicas Running, ready=true, restart_count=0 — **no OOM, no crash, no restart**. (The early "Startup probe failed: connection refused" warnings are normal boot-timing noise that cleared within ~30s before the server bound to :8080.)

## FIX (user action — no code change needed)
In Deployment Panel → Secrets, change **`BANKEZEE_CHATBOT_BASE_URL`** from `https://connect.bankezee.com` to the chatbot server host **`https://bankezee.com`** (the code strips a trailing slash; note the in-code docstring references `https://www.bankezee.com`, and preview used the chatbot's preview URL — set whichever host actually serves `POST /api/crm/chatbot/links`). Save and redeploy so the live-slot pod picks up the corrected value.

After the fix, if the chatbot then rejects the request with 502 "Chatbot rejected the CRM key", re-verify `BANKEZEE_CHATBOT_CRM_KEY` matches the chatbot's `CRM_API_KEY`.
