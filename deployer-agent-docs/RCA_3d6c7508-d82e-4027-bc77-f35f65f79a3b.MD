# RCA — /admin/customers-campaigns shows no data + "LIVE SENDING" in production

App: responsive-crm-app-1 (connect.bankezee.com) · DB: `teleconnect-web-test_database` · active run `3d6c7508-d82e-4027-bc77-f35f65f79a3b`
Deployment itself is healthy/live — this is an app-logic + data issue, not a pipeline failure.

## Symptom 1 — GET /api/cc/customers and /api/cc/filter-options return 500 (page empty, "Something went wrong")

### Proven root cause: `KeyError: 'id'` in `sync_customers()`
Production backend logs (active run) show repeated 500s on both endpoints with:

```
Traceback (most recent call last):
  File "/app/backend/routes/cc_core.py", line 200, in maybe_sync
    await sync_customers()
  File "/app/backend/routes/cc_core.py", line 138, in sync_customers
KeyError: 'id'
```

`cc_core.py` line 138 (and line 147) hard-index the loan file id:
```python
base = {"source": "connect", "file_id": f["id"], ...}   # line 138
... "loan_key": f"connect:{f['id']}:{i}", ...            # line 147
```
The Mongo projection requests `id:1`, but **the field is not guaranteed to exist** on every `db.leads` doc with `status:"file"`.

### Data proof (production, read-only)
- `db.leads` with `status:"file"` → **540** docs
- of those, **15** docs have **no `id` field** (`{status:"file", id:{$exists:false}}` → 15)
- `db.meta_leads` FILE docs missing `lead_id` → 0 (the meta branch is fine)

When `sync_customers()` iterates and reaches any of those 15 id-less file leads, `f["id"]` raises `KeyError`, which aborts the whole sync. Every endpoint that calls `maybe_sync()` (customers, filter-options, me) then 500s. Preview works only because its lead data has no id-less `file` docs.

### Fix (Code — E1)
In `backend/routes/cc_core.py`, make the connect-leads loop tolerant of missing `id`:
- Use `fid = f.get("id")` and `continue`/skip the doc if `fid` is falsy, OR backfill before use.
- Replace `f["id"]` at line 138 and `f['id']` at line 147 with the guarded value.
(The meta branch at line 143 `d["lead_id"]` is currently safe but worth the same guard.)
Alternative/also: backfill the 15 `db.leads` `status:"file"` docs that are missing `id` (change_mongo_data) — but the code guard is the durable fix since it prevents one bad doc from taking down the whole sync.

## Symptom 2 — header shows "LIVE SENDING" in production

### Proven cause: stored setting, not a code default
`db.app_settings` doc `key:"cc_settings"` in production:
```
live_sending : true          <-- code DEFAULT_SETTINGS is False (cc_core.py:29)
test_number  : ""            (empty)
birthday.enabled : false
```
So `GET /api/cc/me` correctly reflects the stored doc (`live_sending=true`). This is persisted DB state, not the code default.

### Has anything actually been sent? No.
- `db.cc_messages` count → **0**
- `db.cc_campaigns` → collection does not exist
No messages/campaigns have gone out yet, so there is no delivered-message damage — but production is armed to send live, with an empty `test_number`.

### Fix (User — change_mongo_data / app setting)
Set `live_sending` back to `false` for the production `cc_settings` doc (via the app's settings screen if it exposes the toggle, or a one-off DB edit). Confirm whether live sending was intended; if test sends are expected, also populate `test_number`.

## Summary
1. 500s = `KeyError: 'id'` at `cc_core.py:138` caused by 15 `db.leads` `status:"file"` docs with no `id` → Code fix (guard the id access).
2. "LIVE SENDING" = production `app_settings.cc_settings.live_sending=true` (code default is false); nothing sent yet (cc_messages=0, cc_campaigns absent) → User sets it back to false.
