## Fixes

### A. Code (E1) — defensive coercion in eligibility (primary fix)
In `/app/backend/routes/bank_policies.py` around line 537, coerce policy thresholds to numbers before comparison (e.g. `max_bt_count = int(max_bt_count) if str(max_bt_count).strip().isdigit() else None`), and apply the same coercion to all numeric policy fields used in comparisons (`min_salary, min_cibil, max_foir, max_tenure, roi_min, min_loan_amount, max_loan_amount, max_bt_count, min_emis_paid`). This makes eligibility robust to any policy field saved as a string (the Policies admin UI is evidently letting a string through). Requires a redeploy.

### B. Data (user / DB Manager) — fix the bad policy value
Edit the **AU Small Finance** `bank_policies` document: change `max_bt_count` from `"3"` (string) to `3` (number). This unblocks the eligibility check immediately for all leads even before the code fix ships.

### C. Form 16 ChatError — needs more signal (user + code)
- **User:** click **Reprocess** on the two Form 16 docs — the batch logs indicate a transient per-request LLM-gateway (LiteLLM/emergentintegrations) failure, not a systemic config problem (other docs in the same batch extracted fine).
- **Code (E1):** the handler swallows the ChatError and logs only the class name — add the exception's message/response body to the log (or `litellm._turn_on_debug()`) so the real cause (rate-limit / provider 5xx / timeout / safety block) is visible if it recurs. The current logs do NOT contain enough to name the cause.

Note: tier_0; one `/health` upstream timeout was seen in-window — unrelated to this lead but worth watching if eligibility/extraction load grows.
