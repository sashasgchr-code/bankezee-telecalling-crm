- `whatsapp.last_error.code = 132018` "There's an issue with the parameters in your template", Graph http=400.
- The send reached Graph (fbtrace present, http=400) — so recipient, header media and URL-button token were all present (the code returns `no_token`/`link_failed`/`header image upload failed` BEFORE calling Graph; none of those happened).
- full_name = 'Ganesh Majji' is CLEAN: regex probes for [\n\t\r], 5+ spaces, and \u00a0/\u2007/\u202f/\u200b (nbsp/zero-width/unicode spaces) all returned 0 matches.
- Across the whole collection: 6 leads have whatsapp.status=failed + code 132018; 0 of them have a full_name containing \n, \t or 5+ spaces.
- => The hidden-character theory is disproven, and the `clean_param()` sanitizer added in this deploy does NOT address this failure (the name was never the problem). 132018 persists because the OUTBOUND TEMPLATE PAYLOAD does not match the approved Meta template definition — not because of the parameter text content.

The exact mismatched element cannot be read from here (no access to Meta WhatsApp Manager). Most likely candidates for #132018 on a clean name:
- The body component is sent as a NAMED parameter: `{"type":"text","parameter_name":"customer_name","text":...}`. If the approved `loan_application_response` template uses POSITIONAL variables ({{1}}) or a different variable name, Meta rejects with 132018.
- The URL-button component (`sub_type":"url","index":"0"`) or the image header does not match the approved template's component layout.
